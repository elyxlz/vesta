# AGENTS.md

How the system is built, the principles that govern it, and the rules every agent follows. Install/setup lives in [`README.md`](./README.md).

## Project Overview

Vesta is an AI guardian angel: the live agent that runs inside a Docker container, powered by Claude Code, monitoring notifications, responding to messages, and handling tasks autonomously. **"Vesta" always names that running agent, never this codebase.** This repository is the software that builds and runs Vesta: the `vestad` daemon on the host, the harness (`agent/core/`) that drives Vesta in the container, and the client apps. Name those by their component, never "Vesta"; the code that interacts with the live agent is the harness. Vesta drives Claude through the official **Claude Agent SDK** (`claude-agent-sdk`): `core/client.py` builds a `ClaudeAgentOptions`, opens a `ClaudeSDKClient`, and streams response blocks back from the SDK message stream and its native hooks.

Vesta's capabilities come from **skills**: self-contained directories (a `SKILL.md` plus scripts) loaded on demand, covering messaging, tasks and reminders, email, web browsing, and more, with each agent activating the ones it needs. See Adding a skill below.

> **cc_sdk is dormant, leave it alone.** `agent/core/cc_sdk/` drives the interactive `claude` CLI inside tmux behind the same `ClaudeSDKClient` lifecycle, message/block types, hook plumbing, and MCP registration, retained as an alternative driver. It ships in the image but nothing in `core/` imports it. Swapping it back in is not a one-line change: `core/` also depends on `claude_agent_sdk`'s `ProcessError`, which cc_sdk does not define. Do not delete it, tidy it, or wire it back in without an explicit ask. Keep its transport tests (`tests/test_cc_sdk.py`, `tests/test_e2e_transport.py`, `tests/test_stop_race.py`) green.

## Architecture

The `vestad` daemon runs on the host (manages Docker containers, serves the HTTP+WS API); the web, desktop, and mobile apps connect to it. On its first run `vestad` bootstraps itself as a systemd user service and prints the connect link plus a QR code. The Python agent runs inside the container.

- **Agent** (`agent/core/`): async Python. Entry point `main.py`, core loop in `loops.py` (message processing, notification monitoring), HTTP + WS server in `api.py` (the `/ws` bus plus `/status`, `/history`, `/config`, `/provider`, `/memory`).
- **Server** (`vestad/`): standalone Rust crate. `vestad/tests-integration/` (crate `vesta-tests`, a workspace member) is the shared harness only; the end-to-end suites are `[[test]]` targets of the `vestad` package under `vestad/tests/`, so cargo builds the binary for them.
- **Client Core** (`apps/core/`): `@vesta/core`, the shared TypeScript controller every view consumes. Owns the client side of the sync protocol (wire types locked by fixture round-trips, the replica store + reducer, the reconnecting `/sync` socket and the replay-free chat socket, the http client, intents with client ids), the shared chat/roster models, pacing, and notification-content parsing. A separate `@vesta/core/react` hooks entry keeps the root framework-free.
- **Web App** (`apps/web/`): React + TypeScript SPA served by vestad at `/app` and embedded in the desktop app. Components in `src/components/`, providers in `src/providers/` (thin views over the `@vesta/core` controller). Runtime detection and every native capability live in one bridge (`src/lib/native/`) with `electron` and `browser` implementations.
- **Mobile App** (`apps/mobile/`): Expo/React Native app for iOS and Android, a native view over the same controller (RN socket + AppState adapters, stale-while-reconnecting roster/chat holds so backgrounding never blanks the UI). Part of the shared `apps` npm workspace and lockfile; the dashboard renders in a WebView on the service plane.
- **Desktop App** (`apps/desktop/`): Electron wrapper around `@vesta/web`; a TypeScript main process (`src/`: window chrome, preload bridge, connection store, PKCE loopback, self-updater), no frontend code of its own. It self-updates to the latest published release on its own (checked on launch, downloaded in the background, applied on the next relaunch), independent of the gateway. Updating the gateway is a separate, deliberate action (the UpdatePill).
- **Skills** (`agent/skills/` + `agent/core/skills/`): each is a directory with `SKILL.md` + scripts. `agent/core/skills/` holds built-ins shipped with the agent (e.g. `upstream-sync`); `agent/skills/` holds the rest. Every skill lives on disk (the box is a full checkout), so a skill is active or inactive with no install step: `VestaConfig.active_skills` lists the active optional ones, and the boot entrypoint rebuilds `~/.claude/skills` (the symlink farm Claude Code discovers skills from) each boot, core skills always. `skills-activate` adds a name, `skills-deactivate` removes it; instant, offline, effective after restart. Skills are plain directories, not MCP servers; the only MCP server is the agent's own native tool registry (`core/tools.py`), exposed in-process via `create_sdk_mcp_server`.

### Key Flows

**Agent creation**: `POST /agents` allocates a WS port, mints an agent token, writes `~/.config/vesta/vestad/agents/{agent}.env`, and creates the container on its own bridge network (`vesta-agent-{user}-{agent}`), which is what port-isolates agents from each other, with that env file bind-mounted read-only at `/run/vestad-env`.

**Agent lifecycle (vestad owns it)**: containers run Docker's tiny init as PID 1 so detached skill daemons are reaped, plus `on-failure:5`, so Docker recovers a crash but never auto-starts a stale container on daemon/host boot. `reconcile_containers` (`docker.rs`) runs in order: resume interrupted rebuilds; ensure env files; rebuild any container whose config (entrypoint/mounts/network/devices/init) drifted (snapshot + recreate); then migrate policy to `on-failure` in place (`docker update`, never itself a rebuild trigger), start each agent whose desired-run state is running, stop any user-stopped one that's up, and restart already-running agents when this boot re-extracted the embedded core. Rebuilds finish before starts, so an agent needing one is never reachable on its pre-update container. The one exception is a critically full disk: rebuilds are skipped and deferred to the next boot while boot-start still runs, since starting an existing container is not write-heavy. Desired-run state is `user_desired` (`running`|`stopped`, default running) in vestad's `settings.json` and survives reboots. The agent never exits to restart itself, since under `on-failure` a clean exit would stay down: `restart_vesta`/`stop_vesta` (`core/tools.py`) and the dreamer's post-compaction restart call vestad with the agent's `X-Agent-Token` (`core/vestad_client.py`, self-scoped) and vestad performs the docker action. Only a crash uses the exit code: `main()` exits non-zero, Docker init propagates that exit code, and `on-failure` restarts it.

**Client protocol (three planes)**: clients talk to vestad only; vestad is the single client-facing contract producer.
- **State plane**: one multiplexed WebSocket, `GET /sync`. Carries `hello {version, min_supported}`, an immediate tail-less snapshot (gateway + agent roster incl. mid-build agents + pending notifications), in-band `reauth`, and typed deltas (`state`, `agent`, `agent_removed`, `notifications`, `user_notification`, `presence`, `devices`). A fleet-state projection with one narrow upstream channel: no `watch`/`unwatch`, no per-agent live edge, no chat, but clients send a `client_context {focused, client, resync, device_id, descriptor}` frame up (`client` in `web`|`mobile`|`desktop`) and vestad broadcasts a `presence {any_focused}` frame down. This is the first client to vestad to agent information flow, built to carry more over time (e.g. location); a per-connection presence registry (`vestad/src/sync/presence.rs`) aggregates the global focus boolean, and the socket lifecycle owns each entry, so no heartbeat or TTL. Every device vestad has seen is separate gateway-global tree state (`Tree.devices` + the `devices` delta), keyed by the client-minted installation id: `vestad/src/device_registry.rs` is its single owner (the `devices.json` store, the in-memory map, a live-connection refcount that decides `present`, and the roster watch), fed identity plus connect/disconnect by `sync/presence.rs` and the mobile push facet by `mobile_app.rs`, neither writing the file, with the push token never projected onto the wire. `devices.json` supersedes `mobile-devices.json` (migrated on load); `ClientKind` and `MobilePlatform` are shared device-identity types in `vestad/src/types.rs`. `resync` marks a replay of context the gateway already has, so the return-to-focus notification never fires on a mere reconnect or gateway restart; a report the socket could not deliver (every client reports from a mount effect, so the first one always lands mid-handshake) rides the next open as the fresh focus it is. `user_notification` carries `{agent, kind, title, body}` (`kind` in `message`|`rate_limited`|`gateway_updated`) and is the one ephemeral delta.
- **Command plane**: addressed HTTP intents carrying a client `intent_id`. The chat send intent POSTs to the app-chat service through the proxy (`POST /agents/{name}/app-chat/message`); the skill dedups repeated `intent_id`s and persists + emits before the 200, so the 200 is durable delivery. Delivery truth is the echo carrying that id on the chat socket, never merely the 200; a 502/503/504/timeout is retryable.
- **Service/bulk plane**: the authenticated per-agent proxy, carrying what a state tree cannot: the whole app-chat service (intake, paged id-cursored history `GET .../app-chat/history`, the replay-free live chat socket `GET .../app-chat/ws`), SSE logs, voice STT WS, backups.

Vestad's aggregator (`vestad/src/sync/`) feeds the state plane from one read-only internal tap per running agent (`agent_status.rs`), shrunk to activity + pending notifications + timezone + the `presence_notifications` toggle. User-facing notifications are produced separately: an agent-side primitive (the vestad `user-notification` script the app-chat daemon shells on a reply, or core on a rate limit) loops back to vestad (`POST /agents/{me}/user-notification`, agent-token, self-scoped), which fans the delta to `/sync` clients and, for a reply, an Expo push to backgrounded mobile. One kind has no agent behind it: after boot recovery reports an update that landed, vestad waits out a reconnect grace window (`ANNOUNCE_GRACE_SECS` in `update.rs`, shortened for the e2e by `VESTAD_UPDATE_ANNOUNCE_GRACE_SECS` exactly as `VESTAD_RELEASES_BASE_URL` redirects the release source) and, only if no client connected and focused inside it, publishes a `gateway_updated` user notification naming an empty agent. The agent-injected endpoint refuses that kind, so nothing but a real update produces one, and a client that watched the update instead renders the in-app resolution (`useUpdateResolution` in `@vesta/core/react`, shared by web and mobile). Client presence gates notifications three ways: vestad skips the Expo push while any client is focused, web and desktop mute their own locally-raised notification on the broadcast `any_focused` (so focus on one device quiets the others), and when the user returns after at least ten minutes offline vestad drops a snoozed `source=vestad`, `type=user-presence` notification into every tapped agent with `presence_notifications.enabled` (the tap is where that toggle comes from, so an agent outside it would read as enabled and ignore an opt-out). Agent lifecycle noise is engineered out at three layers, none of them timed: liveness is the held tap connection (`combined_status` reads `tap_connected`, so a running container is `Starting` exactly while its tap is down and a one-shot probe flap cannot exist; a flags fetch that fails keeps the last answer and never demotes a live agent), vestad's planned work registers an operation (`PublishedOperation` in `agent_status.rs`: manual and scheduled backups, restores, vestad-performed restarts; backups and restores ride the roster's `operation` field, a restart projects as the `restarting` status shipped clients already render, and `on_wire` keeps internal operation kinds off the wire), and the mobile `status` push advances a per-agent last-stable-status map (`mobile_app.rs`) only on a stable, unoperated observation taken while observation is armed, which spans exactly the gap between the two ends of vestad's own agent work (the boot reconcile task arms it as its last step, the shutdown branch disarms it before it stops every agent), so a boot seeds silently and a real change (died, stopped, signed out, recovered) pushes exactly once. An `Alive` agent still inside its non-interruptible boot turns additionally carries `booting` on the roster (core counts the batch and reports `boot_complete` on `GET /status`), which clients render as the same "waking up..." the pre-tap boot shows: the whole boot reads as one phase while chat stays open (messages queue durably) and `all_alive_idle` still makes maintenance wait. The agent's own WS event bus is internal: vestad's tap and in-container skills consume it, never clients. Chat tails come from paged history joined to the chat socket's live echo by event id, so a reconnect gap self-heals by refetching the tail by id.

**Client compatibility contract**: the `/sync` hello carries a version window `{version, min_supported}`: the gateway's own version and the oldest client it accepts (`MIN_SUPPORTED_CLIENT_VERSION` in `vestad/src/sync/mod.rs`, serialized in `sync/handler.rs`). `@vesta/core` checks the client's build version on the hello (compare in `protocol/release-version.ts`, decision in `transport/socket.ts`): below `min_supported` raises terminal `app_behind` (`AppBehindScreen`; only the app updating resolves it); above the gateway's `version` raises recoverable `gateway_behind` (`GatewayBehindScreen` with an update-gateway action, self-healing on reconnect once the gateway restarts newer); otherwise proceed. An unparseable version on either side fails open. The client compares its own build version locally and never puts it on the wire: vite dev servers, web bundles embedded in debug vestad builds, and development-variant mobile builds carry the sentinel `dev`, which is unparseable and so never blocks; production web and desktop builds carry the Cargo package version, and production mobile builds carry `Constants.expoConfig?.version`. Unknown frames and fields are ignored by rule, which is what keeps additive evolution from moving `min_supported`:
- **Safe, never move `min_supported`**: adding a frame/delta type, adding fields to a frame, adding a `user_notification` kind, adding a REST endpoint, adding optional response fields. The tests pinning the ignore-unknown rule (`parse.test.ts` "ignores unknown", `socket.test.ts` "ignores unknown frames", vestad's `client_frames_round_trip`) must never be deleted.
- **Breaking, must bump `min_supported`**: removing or renaming a frame/delta/field clients read, changing a field's type or semantics, reshaping a REST endpoint or a chat-socket `StoredEvent` field shipped clients depend on, or changing auth or path contracts on a proxy surface clients use.
- **Fixture gates catch accidental drift, not intent**: a `sync-protocol.json` regen (`REGEN_API_FIXTURES=1`) or event-union regen that reshapes a fixture is the moment to ask "did I just break shipped clients?".
- **Bump procedure**: no client builds exist between the latest published release and the next, so any value in that gap is equivalent. Set `MIN_SUPPORTED_CLIENT_VERSION` to the current version with the patch incremented (shipped `0.1.180` -> write `0.1.181`), in the same PR as the break. If a second breaking PR lands before a release and the value is already in the gap, leave it. This is why it can read one patch ahead of the repo version: deliberate, do not "fix" it. `release.sh` refuses to release when the value is above the smallest version the next bump can produce (current + patch), deliberately ignoring which bump you asked for, so a botched bump that would lock out every client is impossible to ship.

**Message flow**: the app-chat service writes a `source=app-chat` notification file first, then persists the user message to its own store (sqlite + FTS5), streams the echo on its live chat socket, and records the `intent_id`. The notification write is the only fallible side effect, so doing it first keeps intake at-most-once: a failure persists, echoes, and remembers nothing, and a retry with the same `intent_id` re-runs the whole intake exactly once. All of it completes before the 200, so a message the UI echoed as delivered is durable even with no socket connected. All app chat reaches the model through the notification flow below. The agent replies with `app-chat send`, which persists the reply, fans it to connected chat sockets, and shells the vestad `user-notification` script. Core does not transport chat. The processor's queue (`message_processor` in `core/loops.py`) has exactly two producers: notification batches (`process_batch`) and boot turns (`collect_boot_turns`).

**Preemption**: the processor's queue-watcher owns preempt delivery. An item landing mid-turn goes out via `send_preempt` (`core/client.py`) as a `priority:"now"` user message, and the CLI ends the running turn at its next step boundary (a foreground tool call in flight finishes first; the latched abort applies when it returns), with background subagents surviving (issue #982). Delivery is completion: the CLI persists the message on receipt but guarantees no per-prompt result (it merges rapid queued prompts into one turn, starts turns of its own, and its ResultMessages carry no prompt identity), so the watcher clears a delivered item's notification files on the spot and never opens an agent turn for it. Output streams through the session's single consumer, which also keeps activity state honest for turnless work (`_dispatch_message`). Undeliverable items (idle gap, boot turn, compaction, unauthenticated, failed write) queue as ordinary turns with 1:1 query/result pairing. The SDK `interrupt()` fires only on failure paths (silence/query timeout, auth loss), because in headless mode the CLI's handler kills every backgrounded subagent.

**Notification flow**: external systems write JSON files to `~/agent/notifications/`; `monitor_loop` in `core/loops.py` watches with `watchfiles.awatch()`. Each tick `notification_interrupt_policy.py` picks one of three actions (`interrupt`, `snooze`, `trash`) via an ordered first-match ruleset: each rule carries an action, an optional `expires_at` for a temporary silence, and matches on `source`/`type` plus any number of `match` predicates (`FieldPredicate`: a field, `contains`/`regex` op, optional `negate`) over any notification field, with `sender`/`text` aliases spanning per-source synonyms. With no matching rule the notification's own `interrupt` flag decides (`Notification.interrupt` in `notification.py`: whatsapp/chat interrupt, email/finance snooze). Interrupting notifications preempt the current turn; snoozed ones are worked through in one batch once the agent has been idle a little while; trashed ones are moved to `config.notif_trash_dir` and never reach the agent at all, which is the one path by which a user rule can drop input. The ruleset lives on `VestaConfig.notification_rules`, read live from the store each tick and edited by the user (`PUT /config`) or the agent (the `notifications` skill). `source=core` notifications are exempt, their disposition being control-flow derived from the type (`CORE_SNOOZE_TYPES`, decided by `loops._notif_disposition`), so a broad user rule can't swallow them. Boot-time control-flow (greeting, first-start, migrations, skill-sync, config issues) is not a notification: it is delivered as non-interruptible boot turns enqueued at startup and processed in order before other work.

**Session persistence**: cross-restart state lives in `~/agent/data/state.json`, a single atomically written `PersistedState` blob owned by `state_store.py` (SDK `session_id`, boot markers, `applied_migrations`, last dreamer run). All events live in `~/agent/data/events.db` (SQLite with FTS5), versioned via `PRAGMA user_version`: `events.py` owns an ordered, version-gated `_MIGRATIONS` list applied at `EventBus` construction. Version 1 is the baseline, so fresh and unversioned dbs both converge to it with no data loss. Version 2 adds the FTS triggers that index inbound-message notifications by `$.summary` (excluding `source=core` boilerplate) and backfills the history already stored, which is what lets the `recall` skill search the user's own words and not only the agent's. Further changes add v3+ steps, and a released step is never edited, so a step spells out its own SQL predicates rather than sharing a constant a live query can change under it. Every restart resumes the persisted `session_id`; only compaction shrinks context. Compaction is one core primitive, the `compact_context` tool (`core/tools.py`): compact the live session at the next idle point with caller-supplied instructions, optionally deliver a follow-up turn, optionally restart into the compacted session. The drain (`loops.py:drain_compaction_request`) owns that routing and prepends the core-owned orientation line (`COMPACTION_ORIENTATION`); `compact_session` (`core/client.py`) appends the core-owned credential guard (`COMPACTION_CREDENTIAL_GUARD`) to every `/compact`'s guidance, whatever the caller supplied, so a core-issued compaction's summary never reproduces a credential into the compacted context (the CLI's own auto-compaction does not route through it). The nap skill (compact in place) and the nightly dream (curate memory, `mark_dreamer_complete`, then `compact_context(restart=true)`) compose on top: core owns only the mechanism, a generic once-consumed `pending_boot_message`, and the `last_dreamer_run` timestamp, never the feature's meaning. The dreamer runs nightly at `NIGHTLY_MEMORY_HOUR`.

**Migrations** (agent-state, distinct from the events.db schema migrations above): `migrations.py` runs prompt-based migrations, markdown files under `agent/core/migrations/`. A migration defaults to `after_sync`; select either phase with `---\nmigration_phase: before_sync|after_sync\n---` frontmatter. Pending before-sync migrations are delivered together as an exclusive boot barrier, then the runner restarts: later boots retry anything left unmarked and only proceed when the phase is clear. Upstream sync runs next, followed by all pending after-sync migrations as ordered boot turns: the non-interruptible batch first, then the interruptible batch. An after-sync migration can declare `interruptible: true` in its frontmatter (default false, rejected on before-sync migrations): user messages can preempt the interruptible batch, and unmarked migrations re-run next boot as always. If sync merged changes, its restart leaves the still-unmarked after-sync batch for the next boot; a no-op sync falls straight through to it. Each migration's final step calls `mark_migration_applied(name)`, recorded in `state.json`. A migration-local stop skips only that section, and requested restarts wait until the batch has been processed. If the agent never marks a migration (rate limit, crash, hallucinated success) it re-runs next boot, so migration prompts must be idempotent. Fresh agents pre-mark every shipping migration without running it; migrations exist only to converge legacy state on update. Released migrations are append-only: once shipped they never re-run for already-migrated agents, so an edit reaches nobody. Converge new state with a new migration file, never by editing a shipped one, and make each migration cumulative (the beta channel lets agents skip versions; never assume the previous version was N-1).

**Upstream sync (vestad-local distribution)**: vestad embeds the complete agent home. At startup `upstream.rs` runs the embedded `vestad/scripts/build-upstream.sh` (one tested bash script owning all git logic; suite in `agent/tests/test_build_upstream.py`) to append a snapshot commit + `agent-vX.Y.Z` tag to the per-host bare repo at `~/.config/vesta/vestad/upstream/upstream.git` (branch `agent-upstream`). That directory is bind-mounted read-only into every container at `/run/vesta-upstream` and boxes fetch straight from it: no github, no network, no auth, identical in dev/tests/prod. A box's `$HOME` is a plain full checkout of that branch (`attach.sh`), holding `agent/skills/` plus `agent/MEMORY.md`, no sparse-checkout. `agent/core/` is deliberately excluded from the snapshot (build-upstream copies the whole embedded home, then removes `core/` and writes a root `.gitignore` scoping it out), so the read-only engine mount is the only source of core and never shows as untracked. That generated `.gitignore` is load-bearing: it is also what keeps `~/.claude` untracked on a box. After an upgrade, `upstream_sync.py` asks Git whether `agent-v<version>` is in `HEAD` and queues a boot turn when it is not. The skill exposes the real operation instead of a wrapper: fetch, checkpoint dirty work, then `git merge --no-ff --no-edit agent-v<version>`, preserving the agent's commits behind one visible update boundary. There is no status wrapper and no synced-state marker, because Git ancestry is the truth: interrupted or forgotten updates re-fire on their own while the tag is missing. A box paused mid-merge must finish or abort it, never checkpoint it. `attach.sh` (birth, interrupted-birth recovery, flat-checkout migration), `fetch-upstream.sh`, `set-cone.sh`, no-op marker aliases, the forwarding `workspace-sync` paths, the `agent-workspace` branch, and the `workspace.bundle` endpoint all remain as fleet compatibility. **Testing on dev**: prefer unit and integration tests, since releases normally bump the version; for same-version iteration, restart vestad (which moves the tag) and ask the agent to sync, or run `vestad serve --standalone --force-update`, which restarts every running agent into a fresh boot (before-sync migrations, upstream-sync, after-sync migrations) even when the embedded agent code is unchanged.

**Config (two bricks, one home each)**: configuration is split by kind so each value has a single owner.
- **Identity** (`WS_PORT`, `AGENT_TOKEN`, `AGENT_NAME`, `BOX_HOST`, tunnel): vestad writes it to `agents/{agent}.env` on the host at creation, bind-mounted read-only into the container; the agent never writes it. The agent's timezone is not identity: it lives in the config store and the agent applies it at boot.
- **Config**: a single nested store at `~/agent/data/config.json`, modeled by `config.py`'s `VestaConfig`. It holds the active `provider` (a pydantic discriminated union of Claude, OpenRouter, Z.AI, Kimi, and OpenAI configs, carrying model, context, and provider-specific auth/settings), provider-independent prefs (`agent_personality`, `timezone`, `seed_context`, `active_skills`), and `notification_rules`.

The provider is its own resource: `PUT /provider` (sign in), `PATCH /provider` (model/context/thinking), `DELETE /provider` (sign out); `PUT /config` writes prefs and `notification_rules` and rejects a `provider` key. Most `PUT /config` fields apply on the next restart; `notification_rules` apply live. `VestaConfig` layers pydantic-settings sources, highest first: init args, the config store, env (identity + operational scalars only), then field defaults. New-agent defaults plus the per-provider catalog (provider display names, order, auth kind, model lists, context policy) are hand-authored in `agent/core/manifest.json`, read by `config.py` as the one source of field defaults and served at `GET /manifest` for the non-Python clients; there is no generation step. A fixed-catalog provider's manifest entry carries its model list plus `model_names`, so the manifest names those models in every client. A provider marked `models: "live"` carries neither: OpenRouter's catalog comes from OpenRouter, and Claude's comes from the Anthropic Models API, read by the agent's `GET /provider/models` with the stored OAuth token (settings) or by vestad's `POST /providers/claude/models` with the browser-held credentials (onboarding, before the agent signs in). Claude's two floating aliases (`opus-latest`, `sonnet-latest`; agents provisioned earlier persist the bare `opus`/`sonnet`, which stay valid) and their labels are owned by `CLAUDE_ALIASES` in `@vesta/core`, offered ahead of the expandable live list in every picker, and `opus-latest` is the code-owned Claude default since a live entry has `default_model: null`. `provider_harness_model` strips the `-latest` suffix, so the CLI receives the bare alias it resolves itself; the resolved concrete model is reported back on `GET /provider` as `resolved_model` so clients label an alias with the exact model it runs as. Built-in prompts ship in `agent/core/prompts/` (`core_prompts_dir`); the agent's MEMORY.md lives at `~/agent/MEMORY.md`.

**LLM provider**: each agent selects one provider in `config.provider`: Claude OAuth (the default), OpenRouter API key, Z.AI Coding Plan key, Kimi Code membership key, or OpenAI ChatGPT OAuth. The discriminated union makes provider-specific shapes explicit: key-backed providers require a redacted `SecretStr`, Claude owns the thinking knob, OpenAI has no API-key field. `provider.py` owns validated, rollback-safe sign-in/switch/sign-out writes. Claude OAuth lives in `~/.claude/.credentials.json` for the Claude CLI to refresh; ChatGPT OAuth in `~/agent/data/claude-code-proxy/codex/auth.json`; key-backed credentials in the config store. Switching deletes inactive OAuth, enforced at boot after the previous harness stops. `client.py` maps the provider to a harness transport: direct Claude, OpenRouter's local cache proxy (`openrouter_cache.py`), Anthropic-compatible Z.AI/Kimi endpoints, or the pinned local `claude-code-proxy` bridge for a ChatGPT subscription. Provider writes are write-only and the caller restarts once to apply. Auth state is re-derived from the store plus the provider's external credential file on every boot; runtime terminal failures flip it in-memory only, with provider-aware handling where status codes are overloaded (notably Kimi). **Invariant: the git workspace must never track `~/.claude`.** The agent's `$HOME` is a git checkout of the upstream snapshot, and `~/.claude` is also its runtime dir (credentials + sessions). The snapshot's generated root `.gitignore` excludes everything but `agent/` (minus `core/`), so a plain checkout never touches the credentials and no skill script or migration needs a per-call guard.

**Auth**: vestad generates an API key at `~/.config/vesta/vestad/api-key` (clients use a `Bearer` token or `?token=` query param, or exchange it at `POST /auth/session` for a short-lived JWT access token). TLS uses self-signed certs with no CA chain; vestad computes and persists a SHA-256 fingerprint, but only the Rust test harness pins it (mobile requires a CA-trusted tunnel instead). **vestad is the single gate for private services**: a service registered `public: false` verifies nothing itself, it serves whatever the proxy forwards, and the decision is vestad's alone (`auth::proxy_authorized`, joined by `agent_proxy::keyed_forward_path` for the path carrier, which also strips the prefix it just authorized). The proxy strips every gateway-auth carrier before forwarding, so an upstream never sees the credential that opened it: the `Authorization` header and each `token=` query pair are dropped (`forwarded_query` in `agent_proxy.rs`) exactly as `keyed_forward_path` drops the path prefix, both reading the same `CLIENT_CREDENTIAL_HEADER`/`CLIENT_CREDENTIAL_QUERY_PREFIX` consts the gate reads (`auth.rs`) so the two cannot drift; a third carrier added to the gate must be dropped here too, since nothing yet iterates one shared carrier list (pinned in `vestad/tests/server/service_keys.rs`). A private service accepts the api key or an access token, either one as an `Authorization: Bearer` header or a `?token=` query param, or a service key scoped to one service on one agent, which those two carriers take and which is additionally accepted as a `/k/{key}/` prefix on the service subpath. Only a service key opens that path form (`keyed_forward_path` asks the key store and nothing else), so an api key in a URL prefix falls through to `proxy_authorized`, which reads headers and query alone, and 401s. The path form exists because a relative iframe sub-resource inherits a path prefix but neither headers nor a query string, so a keyed page's assets authenticate exactly as the page did. Service keys (`service_keys.rs`) are hashed at rest (the secret exists only in the mint response), expire after a default 30 days unless the caller sets `ttl_secs` or opts out with `never_expires`, and are revocable by id; the agent mints and revokes them for its own services (`POST`/`DELETE /agents/{me}/services/{service}/keys`, self-scoped), so it can hand a link to a consumer holding no app credentials. Each agent's unique `AGENT_TOKEN` is the `X-Agent-Token` header for agent-to-vestad calls, and vestad's own inner-proxy credential for the raw agent port alone, whose one consumer is the agent's API in `core/api.py`; it is never a client credential for a service, and the proxy never forwards it to one (`injected_agent_token`, proven end to end in `vestad/tests/server/service_keys.rs`). `public` remains, for a page that must load with no credential at all: the whatsapp QR link page, `file-host`, the `agentmail` webhook, and the browser handover page. A public service is deliberately ungated by vestad, so it must carry nothing sensitive and anything new is private plus a service key; the one outstanding exception is the `agentmail` webhook, which takes unauthenticated inbound email from an external sender that cannot hold a key and so keeps its own `?secret=` check (`agent/skills/agentmail/cli/src/agentmail_bridge/serve.py`). One client surface puts a full access token in a URL query param and this standard does not cover it: the `/sync` state socket every client opens on launch (`apps/web/src/providers/ControllerProvider/index.tsx`, `apps/mobile/src/controller/build-controller.ts`), where the query param is the normal browser pattern rather than a leftover, since a browser `WebSocket` sends no headers. A service key does not reach it, because `/sync` is a gateway route rather than a service. Each app stamps that access token in exactly one place, `websocketUrl` (`apps/web/src/lib/authed-url.ts`, and the same accessor on mobile's `ApiClient`), async so an expiring token is refreshed before it can reach a URL, the same pre-flight the http client runs. That one owner carries the access token and nothing else: a private service's URL takes a minted service key instead, stamped by `serviceKeyQueryUrl`/`serviceKeySocketUrl`/`serviceKeyPathUrl` in `@vesta/core` (the voice TTS stream and STT socket, the dashboard frame, the app-chat live socket), so a full-privilege credential never rides in a media or socket URL pointed at a service. Both log routes are ordinary header-authenticated reads instead: `readSse` (`apps/core/src/transport/sse.ts`) streams over the fetch its caller injects, and each app injects its own http client (`apps/web/src/api/log-stream.ts`, `apps/mobile/src/agent/LogsPage.tsx`), so the agent log SSE and the gateway log SSE present `Authorization: Bearer` and inherit that client's refresh pre-flight and 401 retry. A service-key URL is built per connect rather than captured at mount, so a socket reconnecting hours later re-reads the cache and dials with a re-minted key; the cache (`apps/core/src/service-keys/service-keys.ts`) hands out only keys with more than an hour of life left, and a consumer the gateway refuses `drop`s its key so the next attempt mints. The chat socket is what that is for: a handshake that closes before it opens is the only refusal signal a `WebSocket` exposes (`onClosedBeforeOpen` in `apps/core/src/chat/chat-socket.ts`), and without dropping the key the backoff would present the same refused one forever. That signal fires once per streak, re-armed by a successful open, because most pre-open closes are not about the credential at all (a stopped agent 503s the upgrade for as long as it is down) and re-reporting would mint a key per backoff tick.

**Constitution**: each agent has a user-authored `constitution.md` (host `agents/{name}.constitution.md`) bind-mounted read-only at `/root/agent/constitution.md`, in a separate mount from the core-code mount (`/root/agent/core`) so agent self-updates never touch it. The agent reads its constitution but cannot edit it: the user's immutable rules.

**Backup/restore**: each backup is a `restic` snapshot in that agent's own deduplicated, compressed, encrypted repository at `~/.config/vesta/vestad/restic-repo/<agent>` (one passphrase for all, alongside at `restic-password`). Repos are per agent so concurrent backups of different agents never contend on a shared restic lock. A snapshot is a `docker export` streamed into `restic backup --stdin`, tagged `agent:<name>` + `type:<backup_type>` (pre-update snapshots add `from-version:<vX.Y.Z>`), and never stops or restarts an agent: a running container is captured with `docker commit` (Docker pauses it for the seconds the commit takes) and exported through a temp container, a stopped one exports directly. Restore is `restic dump | docker import` into a fresh container. Dedup means many snapshots of a multi-GB agent cost roughly one full copy plus per-run diffs. `restic` is located on PATH or extracted from a copy embedded into the vestad binary at build time (`build.rs` vendors it into `vestad/vendored/`, `src/vendored_bin.rs` bakes it in, `src/restic.rs` extracts it; same mechanism as cloudflared). Scheduled work runs as one idle-gated maintenance cycle (decision logic in `maintenance.rs` + `maintenance_window.rs`, the pass itself in `serve.rs`): it fires in the fleet's best-coverage 4-5am agent-local window (after dreams), at the first 15-minute poll where every alive agent is idle or at the window's last poll, takes a periodic snapshot of each agent with no fresh auto snapshot (`auto_backup.every_n_days`, default 3), and, when auto-update is on and a release is pending, starts the gateway self-update below as the same cycle's add-on and waits for it to settle. Retention (the 2 newest periodic snapshots and the 2 newest distinct pre-update version sets by default) is computed in `compute_backups_to_delete` and applied via `restic forget --prune`. The separate `vestad backup export/import` file path (`.tar.gz` via `docker export`) is for cross-machine transfer. All `~/agent/` state survives backup/restore.

**Gateway self-update (one durable operation)**: a manual update (the UpdatePill's `POST /gateway/update`, also exposed to agents) and the scheduled auto-update run through one orchestrator in `vestad/src/update.rs`. The endpoint answers as soon as vestad decides (202 started, 200 already current, 409 naming the live phase, 503 when the release check cannot answer, 400 in dev mode); the update itself runs on its own task through three phases: per-agent `from-version`-tagged rollback snapshots (sequential, each bounded by the pre-update budget restic owns, so a wedged export is killed and reduced to a warning rather than stalling the update), the binary swap, and the systemd restart. `systemctl restart` on vestad's own unit kills the systemctl child together with this process, so an error from it is what success looks like: `restart_self` waits a grace window for the shutdown signal (`AppState.shutdown_tx`, flipped by serve's shutdown branch) and, on getting it, reports no failure and leaves the `Restarting` ledger for the next boot to complete; surviving the window is the real failure. `POST /gateway/restart` reads that same adjudication, so a working restart never logs a failure or clears the slot below. The in-memory operation slot is the lock: a second update or a gateway restart is refused with a 409 carrying the phase, while a terminal failure keeps projecting until retried (the same POST; an "already current" answer dismisses it) or dismissed (`POST /gateway/update/dismiss`), but yields the slot. Every phase transition is written to a durable ledger (`update.json` beside `settings.json`) and projected to all clients as the additive `gateway.operation` field on `/sync`, so every device watches the same progress; web locks navigation to home and settings while one runs, mobile shows a single progress sheet. At boot vestad reads and clears the ledger: a target version now running means the update landed, anything else projects as a retryable failure and sweeps the temp backup artifacts an interrupted export can leave behind.

## Architecture Principles

Where canonical architecture advice fights this project's intentional design, the design wins.

- **Elegance is the north star.** Aim for 90% of the value at 10% of the effort. Ambition means scope, never complexity: re-architect without fear, but the final state must end simpler than the start (fewer concepts, lines, states, steps). Subtraction beats addition. Applies to code, architecture, product, and prompts.
- **Deep modules, hidden decisions.** Isolate unavoidable complexity in one module behind a small interface; complexity leaking across module boundaries is the failure mode. The Claude Agent SDK is the model: a small `ClaudeSDKClient` surface hiding the whole headless control protocol. Keep the SDK seam in `core/client.py` + `core/sdk_parsing.py`, do not scatter SDK internals across `loops.py`.
- **Minimize stack depth.** No pass-through wrappers or layers that only forward arguments. Every level between an entry point and its effect must make a real decision; inline the ones that don't.
- **Confine IO to edge modules.** Docker in `vestad/src/docker.rs`, restic in `restic.rs`, the claude driver behind the `claude_agent_sdk` client surface, SQLite + FTS5 in `agent/core/events.py`. No raw shellouts, HTTP calls, or SQL strings scattered into `loops.py`, `client.py`, or request handlers.
- **One owner per decision.** Notification format, the `agents/{name}.env` contract, the SDK option/hook mapping: each lives in exactly one module. A constant or format appearing in two modules moves to its owner.
- **vestad is the single client-facing contract producer.** The apps couple to vestad only through the JSON/WS wire contract (locked by fixture round-trips), the `window.vestaNative` preload API, and the `X-Agent-Token` header. Duplicate small DTO shapes on each side of a seam rather than sharing a library across the boundary.
- **Python stays functional.** Pure functions plus dataclasses/TypedDicts/pydantic models, no classes-with-methods. Pass `State` and `VestaConfig` as explicit keyword arguments.
- **Minimize global state.** No module-level mutable state or singletons: state lives in explicit objects built at the entry point and passed down.
- **Type everything as precisely as possible.** No `Any`/`object` stand-ins in Python, no `any` in TypeScript, no stringly-typed errors in Rust. Model shapes concretely and parse at the boundary.
- **Banned accessors.** No `getattr`, dict `.get()` fallback, or `hasattr` in Python. No `panic!`/`unwrap`/`expect` on fallible paths in `vestad/` (`expect` only where failure is impossible); return `Result`.
- **Named consts, descriptive names, minimal clone (Rust).** Follow `DOCKER_TIMEOUT_SECS`, `IMPORT_PIPELINE_MAX_ATTEMPTS`, `UPSTREAM_READY_POLL_MAX`.
- **Simple data across boundaries.** JSON events on the bus, env vars across the container boundary, serde DTOs across the HTTP API. No request objects, rows, or tmux internals crossing boundaries.
- **High cohesion, no grab-bags.** `helpers.py` and `lib/` stay narrowly scoped; a module whose name needs "and" gets split.
- **Circular dependencies are BANNED.** The module graph is a DAG: if two modules need each other, merge them or extract the shared piece into a module below both. Never break a cycle with an inline/deferred import, a callback registry, or a forward reference; those hide the cycle instead of removing it.
- **Design errors out of existence.** Prefer idempotent no-ops (`unlink(missing_ok=True)`, `mkdir(exist_ok=True)`, restic dedup) over special-case error branches.
- **Surgical by default; restructure when the structure forces a workaround.** Default to the smallest change that solves today's problem: match surrounding style, don't refactor working code for taste, remove only the orphans you create, no speculative flexibility for a single caller. But when a local fix would force duplication, a non-scalable interface, or new coupling, fix the structure instead: the bar for touching more code is "the current shape forces a worse change", not taste. When genuinely torn, lay out both options (blast radius now vs. long-term gain) and let the user choose.
- **One fix per root cause.** Fix at the one layer that causes it; do not stack a redundant defensive guard elsewhere. Overlapping fixes accumulate, the next debugger can't tell which one matters, and each layer masks the next. If a second layer seems necessary you haven't found the root cause. Prefer deleting a now-redundant guard over adding another.
- **Minimize comments; a long comment is a code smell.** Write one only for a non-obvious mechanic the code cannot show (cc_sdk double-Escape, the watchfiles local-stop bridge, the circular dreamer window). If a workaround needs a paragraph to explain, simplify the code instead.
- **Reason about the fleet, not just the repo.** Agents are long-lived containers carrying per-user state and personalization, so a change that is clean in the repo can silently strand them on update. If a change moves, renames, or deletes anything an agent already has on disk or in config, ship an idempotent prompt migration under `agent/core/migrations/` in the same PR, and prefer keeping internal contracts stable to shrink the blast radius.
- **Anything under `agent/` never describes a previous design.** The agent reads, runs, and edits everything there: skills and the CLI code under them, its own engine, the prompts, `MEMORY.md`. It reads all of it cold, so a description of the old system reads as a description of the current one. State the mechanism and the constraint, never what changed; change rationale goes in the commit. `vestad/`, `apps/`, and repo docs are read only by developers and may explain what they replaced. Invoke the `vesta-prompt-guide` skill before editing anything under `agent/`.
- **Mark transitional code for removal.** Code that exists only to converge old fleet state carries a grep-able marker: `LEGACY(remove-when: <concrete, checkable condition>): <what and why>`. The condition must be evaluable later (a version, a date, or a fleet state), never "someday". Enumerate with `rg 'LEGACY\('`; when the condition holds, delete the marked code and its tests in one PR. Prompt migrations are inherently legacy and need no marker; everything else does.

**Deliberately skipped**: circuit breakers, per-dependency bulkhead pools, load-shed 429s, and golden-signal dashboards, because the system is a single-tenant personal daemon where timeout + capped-retry + supervised-restart already bound blast radius. Formal ADR/C4 docs and SCA/SLSA ceremony are replaced by this file plus the memory feedback files. Port/adapter interface objects are replaced by explicit config passing, because Python here is intentionally class-free.

## Karpathy Guidelines

Behavioral rules that reduce common LLM coding mistakes, from [Karpathy's observations](https://x.com/karpathy/status/2015883857489522876). They bias toward caution over speed; for trivial tasks, use judgment.

1. **Think before coding.** State your assumptions explicitly and ask if uncertain. If multiple interpretations exist, present them, don't pick silently. If a simpler approach exists, say so. If something is unclear, stop, name what's confusing, and ask.
2. **Simplicity first.** Minimum code that solves the problem: no features beyond what was asked, no abstractions for single-use code, no unrequested flexibility, no error handling for impossible scenarios. If you write 200 lines and it could be 50, rewrite it.
3. **Surgical changes.** Touch only what you must; clean up only your own mess. Don't "improve" adjacent code, comments, or formatting; don't refactor what isn't broken; match existing style. Mention unrelated dead code, don't delete it. Every changed line traces directly to the request. This governs taste-driven changes only, never a license to work around bad structure.
4. **Goal-driven execution.** Turn tasks into verifiable goals: "add validation" becomes "write tests for invalid inputs, then make them pass"; "fix the bug" becomes "write a test that reproduces it, then make it pass". For multi-step tasks, state a brief plan with a verify check per step.

## Code conventions

### Brand voice
- **Positioning (the single source of truth for Vesta's copy).** Vesta is a **guardian angel**. Not a "personal AI", not an "assistant", not a friend or companion. The canonical one-liner, used verbatim wherever a tagline is needed: **"a guardian angel that gives you back time and helps you achieve your goals."** Every consumer-facing surface (landing, store listings, app strings, prompts, emails, CLI output) draws its positioning from here; never reintroduce "personal AI"/"personal assistant" framing. Technical surfaces such as the GitHub README deliberately retain the more specific "AI guardian angel" framing.
- **Never use a pronoun for Vesta.** Refer to the agent as **"Vesta"**, or **"they/them/their"** where a pronoun is unavoidable. Never "she/her" or "it/its". This holds across every surface: README, app/notification strings, agent prompts and skills, and the vesta-cloud site and emails. The product is a relationship, not a gadget. (This does not apply to other nouns: the daemon, a container, the user, a config object.)
- **No dashes as separators in prose.** In prose and copy (this file, SKILL.md bodies, prompts, app strings, PR descriptions, emails), never use spaced-hyphen or em-dash separators; use commas, periods, or colons.

### Lint enforcement (all languages)
A finding is fixed by changing the code, never silenced. CI enforces the bullets in this subsection plus the ruff, clippy, and eslint rule sets; the language conventions further below are largely reviewer-enforced, so do not read an absent CI failure as permission.
- **Inline lint/type-checker escapes are BANNED repo-wide**: no `# noqa`, `# type: ignore`/`# ty: ignore`, `eslint-disable`, `@ts-ignore`/`@ts-expect-error`/`@ts-nocheck`, `prettier-ignore`, `#[allow(...)]`/`#[expect(...)]`, `//nolint`, or `# shellcheck disable` (guarded by `scripts/check-conventions.py`). When a rule is genuinely wrong for this codebase, tune it once at config level (`agent/ruff.toml`, `[lints]` in the crate's `Cargo.toml`, the eslint config) with a one-line justification; never at the call site.
- **Comment blocks are capped at 8 lines** (a file-leading header block is exempt). A longer comment means the code needs simplifying.
- **Import cycles are enforced**: `scripts/check-conventions.py` keeps `agent/core`'s module graph a DAG; `import-x/no-cycle` covers the web app.
- **Code-smell ceilings**: max 8 args and cyclomatic complexity 15 per function in Python (`PLR0913`/`C90`); max 5 params, complexity 15, nesting depth 4 in TypeScript (web + desktop configs); clippy pedantic (with `unwrap_used` denied) in Rust. Past the ceiling, restructure.
- **Wide rule sets**: ruff runs bugbear, simplify, pathlib, pylint, perf, async, isort and more (see `agent/ruff.toml`); eslint runs `strictTypeChecked` + `stylisticTypeChecked` in core, web, and desktop (mobile extends `eslint-config-expo` only); shell scripts pass `shellcheck -S warning`, which globs `*.sh`, so give a new script that extension to get it linted and escape-guarded.

### Python (agent/)
- **Always `uv run`**, never bare `python`
- **`getattr`, `.get()` (dict), `hasattr` are banned**: use direct access, `in` checks, or try/except
- **`tp.Any` and `object` are banned as loose types** (including `dict[str, Any]`): model shapes as pydantic models or TypedDicts and parse at the boundary; use `pydantic.JsonValue` for genuinely dynamic JSON; `tp.cast` only to a concrete type
- **No silent exception swallowing**: prefer explicit checks (`if path.exists()`) or log the error
- Line length: 144 (ruff)

### Async Python (agent/)
- **No blocking calls in coroutines**: no `time.sleep`, `requests`, sync `subprocess`/`open`/`input`, or inline CPU-heavy work inside an `async def`. Use `asyncio.sleep`, an async client, `create_subprocess_exec`, or `asyncio.to_thread`/`run_in_executor`.
- **Own your tasks**: keep a strong reference to every `create_task` (e.g. a set with `add_done_callback(set.discard)`) and consume its exceptions. Never fire `create_task` as a bare statement.
- **Respect cancellation**: in `except asyncio.CancelledError` do cleanup then re-raise. No unshielded `await` in `finally` cleanup. From a non-loop thread use only `call_soon_threadsafe`/`run_coroutine_threadsafe`.
- **No mutable default args**: default to `None`, build inside the body. Compare to `None` with `is`/`is not`.
- Log with `%`-style placeholders (`logger.info("x=%s", value)`), not pre-formatted f-strings.

### Rust (vestad/)
- **No panics in library/server code**: return `Result`, never `panic!()` or `.unwrap()` on fallible operations. `.expect()` only where failure is truly impossible.
- **Named constants for magic numbers**: timeouts, buffer sizes, port numbers, retry counts go in `const` at the top of the file.
- **Descriptive variable names**: no single-letter vars. Use `name`, `tag`, `client`.
- **Minimize `.clone()`**: move values into closures when possible.
- **Extract repeated patterns**: if 3+ lines appear twice, extract a helper.
- **Error types**: public errors implement `std::error::Error` and are `Send + Sync + 'static`; never `()` or bare `String`. `Display` messages are lowercase, no trailing punctuation, source chained via `Error::source`.
- **Private fields by default**, access via methods; public fields only for plain data structs with no invariants. Keep derivable bounds on the `derive`/`impl`, not the type definition.
- **Eagerly derive** `Debug` (non-empty) plus `Clone`/`Copy`/`PartialEq`/`Default` where correct; `Box` oversized enum variants.
- **Typed args** over unlabeled `bool`/`Option` flags; group args into a struct/builder past ~5 to 7. No lossy `as` casts for fallible conversions (use `From`/`TryFrom`); avoid catch-all match arms when exhaustive handling is feasible. Every `unsafe` block carries a `// SAFETY:` justification.

### Frontend (apps/web/src/)
- **"Agent" terminology everywhere**, never "box". Types: `AgentInfo`, `AgentConnection`, `AgentActivityState`.
- **The `window.vestaNative` preload API is the desktop wire contract**: `apps/desktop/src/preload.ts` and `apps/web/src/lib/native/types.ts` declare it twice and must stay field-for-field identical.
- **Hook placement**: hooks used only by a single provider live in that provider's folder (e.g. `providers/AgentSocketProvider/use-agent-socket.ts`); `hooks/` is reserved for hooks shared across components/providers.
- **Components in folders**: each component gets a folder with `index.tsx` and optionally `styles.ts`. The vendored shadcn primitives in `components/ui/` are the one exemption and stay flat files.
- **No dividers inside cards**: never separate sections within a card with a divider line (`border-t`/`border-b`, `<Separator>`, `<hr>`); group with spacing. A hard preference, not case-by-case.
- **Rules of Hooks**: call Hooks only at the top level of a component or custom Hook. Keep render pure.
- **Effects are a last resort**: compute derived data during render (or `useMemo`), put interaction logic in event handlers. Every Effect has complete deps, one concern, and cleanup for any subscription, timer, listener, or fetch.
- **Stable list keys** from data identity, never array index for reorderable lists; reset state with a `key` prop, not an Effect.
- **Strict TS**: `strict: true`; no `any` (use `unknown` and narrow), avoid `as`/`!` assertions, annotate object literals rather than asserting, strict equality except `== null`, named exports.

## Adding a skill

Two locations: `agent/skills/{name}/` for most skills, `agent/core/skills/{name}/` for built-ins. Every skill has a `SKILL.md` with YAML frontmatter (`name` + `description`):

```markdown
---
name: tasks
description: Tasks, to-dos, reminders, time-based alerts; create and manage. Requires daemon.
---

# Tasks + Reminders (CLI: tasks)

<usage, commands, examples: the body the agent reads when the skill activates>
```

The **`description` is discovery text**: what the agent sees when deciding whether to use the skill. Write it as when to use and what triggers it, never as a summary of the workflow, since an agent that can read the steps from the description will follow those instead of opening the body. Keep it tight.

A skill's command reaches PATH exactly one of two ways. A `cli/` uv-project (an isolated venv) whose `[project.scripts]` declares each console script, installed by `uv tool install --editable`, is used when the command needs third-party packages or when the skill has more than one command (each is one `[project.scripts]` line). The single `<skill>/<skill>` launcher, linked from the skill's own setup (`ln -sf ~/agent/skills/<skill>/<skill> ~/.local/bin/<skill>`, `~/.local/bin` being on PATH), is used when the skill has exactly one dependency-free command (a stdlib-only script or a shell script). The anti-pattern is a command placed any other way (a `bin/` wrapper copied into a system dir like `/usr/local/bin`, a hand-built runtime env): it sits outside both mechanisms and nothing maintains it. Only the four vestad helpers are linked by agent startup. If the skill ships a CLI, put it in a `cli/` subdirectory as its own standalone project: `cli/pyproject.toml` + `cli/uv.lock` for Python, or `cli/go.mod` for Go (whatsapp and telegram, each with its own `check.sh` subcommand and CI job). Put tests in `cli/tests/`, which is what makes `check.sh agent` pick the suite up at all: a CLI without that directory is silently unchecked. Daemon behavior is additionally covered repo-side by the shared conformance harness `agent/tests/test_daemon_contract.py`, one table row per skill. Skills are discovered from disk, so a new one needs no index step; to make it active on every box by default, add its name to `agent/core/default-skills.txt`.

**Every skill command owns one output contract**, daemon or not: stdout carries only the command's successful output, and a command that fails to do its job exits non-zero and prints its failure, in the same shape it prints anything (JSON envelope or plain text), on stderr, so an agent piping stdout through `grep`/`head`/`jq` can never lose the error. Route the stream choice through one owner per binary that decides by outcome (the model is `emit(data, exitCode)` in the whatsapp CLI's `cli.go`), never per-call-site stream picks. An exit code may still carry a documented answer per command (`plex has`, `vestad-health` reporting DOWN): a probe that determines the state has done its job and answers on stdout.

**If the skill runs a background process**, it implements the daemon contract itself, in its own language: no shared runner exists, and `agent/tests/test_daemon_contract.py` is what holds every skill to the same behavior. The duplication is deliberate and a shared lifecycle module is not to be extracted from it: every skill stays independently installable and independently editable by the agent that owns it, in whatever language it is written in, and the contract test is what keeps the copies honest. One command named after the skill with the daemon as verbs on it, `<skill> daemon start|stop|restart|status`, never a script path: a skill with a CLI declares a `daemon` subcommand, and a skill without one is a single executable at `agent/skills/<skill>/<skill>`, which that skill links onto PATH from its own setup (`ln -sf ~/agent/skills/<skill>/<skill> ~/.local/bin/<skill>`), exactly as a `cli/` skill installs its console scripts (`uv tool install --editable <skill>/cli`); only the four vestad helpers are auto-linked by agent startup (`claude_runtime.py`). A skill's command is its directory name, always; the ssh tunnel is named `ssh-tunnel` so its command does not shadow the system `ssh`. Each verb prints one line of JSON (`{"status":"started"}`/`already_running`, `stopped`/`already_stopped`, `{"running":bool,"port":int|null}`) or fails with `{"error":...}` on stderr and a non-zero exit. Records are `~/agent/data/daemons/<name>.{pid,port}` and the log is `~/agent/logs/<name>.log`, under one name per daemon (normally the command; `voice-keys` names its daemon `voice`), and the budgets are `DAEMON_READY_TIMEOUT_SECS`/`DAEMON_STOP_TIMEOUT_SECS`; boot clears the records dir (`_clear_daemon_records`) because a stale pid can be reused. The pid record is `<pid> <starttime>` (field 22 of `/proc/<pid>/stat`), so a pid recycled inside one container lifetime cannot read as the process that was recorded; a writer with no readable `/proc` writes the pid alone and readers trust that form, and every reader takes the pid from the record's first field. Start is idempotent, fails closed (an unregisterable or never-ready daemon is killed and its records removed), and returns only once ready; stop is SIGTERM then, two thirds of the way through the one `DAEMON_STOP_TIMEOUT_SECS` budget, SIGKILL to the recorded pid (whatsapp deliberately excepted: a SIGKILL mid history sync risks a device re-pair, so it reports a daemon that will not go); status reads the records and never calls vestad. Two per-skill obligations: a port-serving daemon calls `register-service <name>` itself (`--public` only for `file-host`, the `agentmail` webhook, the whatsapp link page, and the browser handover page, pinned by `agent/tests/test_service_exposure.py`), and a daemon that writes a `daemon_died` notification suppresses it for SIGTERM in-process, with no marker files anywhere. The spec the agent reads lives in `agent/skills/vestad/SKILL.md`.

## Testing strategy

- **`check.sh` is the only entry point.** CI calls the same subcommands, so local equals CI. Do not add a CI step that bypasses it.
- **Keep the pyramid.** Fast in-process pytest and Rust `--bins` unit tests are the default loop; Docker-gated suites are the middle tier; `live` (real Claude) is the tiny apex run only on release. Do not push Docker- or Claude-dependent assertions into the fast tiers.
- **Prefer the high-fidelity fake over mocks.** Drive cc_sdk tests through `tests/fake_claude.py` (a real fake claude TUI in real tmux) and exercise the real EventBus/SQLite. Reserve patching for true edges (file times, credentials presence). Keep `fake_claude.py` faithful to the real claude protocol.
- **Hermetic and deterministic.** Each test builds its own tmpdir db / notifications dir and passes in isolation and any order. No shared `events.db`, no wall-clock ordering, no dependence on a running agent.
- **Never `sleep()` to await a condition.** Poll with a timeout (`tests/wait_util.py`) or drive the event-driven loops via their `asyncio.Event` signals.
- **Test observable behavior through public surfaces.** Emit an `AssistantEvent` and assert the resulting event stream or persisted state, not which internal function fired. Behavior names read as sentences.
- **Table-driven tests are fine; keep logic out of test bodies.** Parametrize repetitive cases rather than copy-paste, but no computed expected values or conditionals in the body. The sanctioned exception is hypothesis property tests (`test_property.py`).
- **Beyonce rule, mapped to suites.** Crash recovery / resume -> `test_crash_recovery.py`; preemption -> `test_preempt.py`; failure-path interrupts / compaction -> `test_interrupts.py`; notification batching -> `test_notifications.py`; backup/restore and ports -> vestad tests. If you do not want it to break, it has a test.
- **Coverage is a diagnostic, never a gate.** Do not add a coverage threshold. A line is tested only when a behavioral assertion exercises it.
- **Red is stop-the-line.** A failing master or `check.sh` suite is reverted or fixed forward immediately. Quarantine or fix a flaky test, do not blanket-rerun.
- **Reliability is tested, not assumed.** Every finite timeout, capped retry (`retry_import_pipeline`), single-shot session-resume guard, cancellation path, and `finally`-block resource release has behavioral coverage.
- **Tests ship with logic changes** in the same PR. No permanently skipped or panic-only tests; assert concrete values.

## CI

`ci.yml` runs shared validation on pushes to `master` and PRs, path-filtered on PRs. `release-pipeline.yml` is triggered only by a published prerelease, calls the same reusable CI workflow, then runs the live gate and publishing jobs, so PRs do not show irrelevant skipped release checks. Check jobs call `./check.sh` subcommands, so CI and local checks are identical by construction. The frontend runs as four per-app jobs (`test-app-core`, `test-app-web`, `test-app-desktop`, `test-app-mobile`), each gated on its dependency closure (web needs core, desktop needs core + web, mobile needs core) in the job `if:`, not in the per-app path filters. Checks include version sync across sources, workflow syntax, dependency review, ruff, ty, cargo clippy, pytest, `uv.lock` freshness, the three communication-channel suites (`comms-checks`: the whatsapp/telegram Go CLIs plus app-chat), the `install.ps1` PowerShell check (`check-windows`), and a native mobile compile when native inputs change. `build-vestad` cross-builds the static musl binaries the release pipeline publishes. Mobile PRs validate every EAS workflow against Expo's public schema without authenticating or queuing a cloud build. Electron packages are unsigned on PRs; every non-PR run, including master pushes, signs and notarizes. The single required branch-protection check is `merge-gate-ci`. `security.yml` runs a four-language CodeQL matrix on PRs, master, and weekly, outside the merge gate.

Two CI toggles are currently off and change what artifacts exist: `BUILD_MAC_UNIVERSAL` is false, so macOS builds are Apple Silicon only, and `BUILD_ANDROID` is false, so the native mobile compile covers iOS alone.

Docker-based jobs (integration, vestad Docker unit tests, live) build the agent image **from the checkout** (GHA layer cache) and run with `VESTAD_AGENT_IMAGE=vesta:local`, so PRs are validated against their own agent code and Dockerfile, never the previously released image.

The live agent e2e job runs a real agent against real Claude using the `CLAUDE_CREDENTIALS` OAuth secret in the release pipeline (never on PRs, since it is slow and spends API tokens) and gates publishing artifacts and the versioned agent image; `live-tests.yml` also exposes a `workflow_dispatch` for a manual run against a given ref. Desktop builds from `apps/desktop`: a signed + notarized dmg/zip on macOS, deb/rpm on Linux, NSIS on Windows, plus the `latest*.yml` manifests electron-updater reads.

## Pull requests

- **Never push to master.** Every change lands through a PR, urgent hotfixes included. Pushing to a feature branch needs no confirmation.
- **Work in a git worktree per branch.** Parallel sessions may hold other branches; keep the main checkout clean.
- **One concern per PR.** Isolate renames/moves and dependency bumps (manifest plus lockfile together) from logic changes. Add new dependencies conservatively and justify any new cross-module edge.
- **Conventional Commits** subjects (`feat`, `fix`, `refactor`, etc.), imperative mood, no trailing period, no closing keywords or @mentions in commit messages (those go in the PR body).
- **Do NOT bump versions in PRs**: `release.sh` handles version bumps at release time.
- Run the relevant `./check.sh` subcommands before pushing.
- **A PR is done only when CI is green and it is mergeable.** After pushing, verify mergeability and resolve conflicts; do not report a PR as finished before `merge-gate-ci` passes.
